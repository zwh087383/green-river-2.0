# 工控机 4.0 延迟测试

测试日期：2026-10-19，主测试 17:20:22—17:21:31（北京时间）。

## 结论

在 `172.16.40.215` 工控机上，当前 800 ms 断句配置下，5 次完整语音请求全部成功。“说完到收到第一段回复 PCM”的中位数为 **2.739 秒**，范围 **2.521—3.278 秒**。这测的是服务端链路，尚未实测扬声器出声延迟。

本机检索中位数 139 ms，且 5 次语音请求全部复用识别期间的检索预取。主要等待集中在断句、Qwen 结束判断、云端语音回复。CPU 和内存采样未显示本机资源饱和。

仅在测试请求中把断句时间改为 400 ms 后，3 次结束识别等待的中位数从 800 ms 降至 450 ms，节省约 350 ms。**正式配置仍为 800 ms，未修改业务代码，也未修改 3.0。**

## 环境与方法

- 项目：`/home/nerv/green-river-4.0`，服务 `127.0.0.1:8001`。
- Ubuntu 22.04，Python 3.10.12，Core Ultra 5 125H，16 GB 内存；本地 embedding 使用 CPU。
- ASR：`qwen3-asr-flash-realtime`；结束判断：`qwen3.7-flash`；文字及语音回复：`qwen-audio-3.1-realtime-plus`，音色 `longanqian_v3.1`。
- embedding：`google/embeddinggemma-2`，768 维。当前实际已索引知识库为 1 个文档、3 个向量块；检索耗时不能代表大规模知识库。
- 基准程序直接在工控机运行，HTTP/WebSocket 通过 loopback 访问，包含工控机到云服务的网络等待，不包含其他电脑到工控机的局域网访问时间。
- 服务已经运行并预热，所有请求串行，使用独立 `latency-*` 会话，不使用真实用户的对话历史。
- 测试音频为仓库已有的合成录音 `samples/audio/question_green_river.wav`，内容“介绍一下绿色江河”，单声道 16 kHz PCM16，长度 2.136 秒。
- 按 100 ms 一帧、真实时间发送，第一帧在第 100 ms 发送；录音后持续发送静音，等待自动断句，没有发送强制 `stop`。
- “说完”的基准采用最后一个 RMS >100 的 20 ms 窗口末端，估计为录音开始后 2.080 秒。它是音频能量估计，非人工标注；若改用完整录音末端计算，下述完整链路延迟均减少 56 ms。
- 收到 ASR final 后携带检索 token 请求 `/api/answer/stream`，记录首文字、首音频及生成完成时间。未录制麦克风、未播放回复，也未启动机器人动作。

五次识别最终文本均为“介绍一下绿色江河。”，云端 ASR 未发生本地回退。回复均有 PCM 和 final 事件，结束判断来源均为 Qwen。回答长度为 102—127 个字符（含标点），约 100 字提示词是软约束。

另外测了 3 次纯文字输入、语音回复：提交到首音频中位数 2,038 ms，范围 1,991—3,307 ms。第一次样本较慢，但没有重启服务，因此不能称为冷启动数据。

告别句“好的先这样，再见”单独测试 1 次：Qwen 正确判为结束，绕过检索；结束判断耗时 1,924 ms，提交到首音频 2,646 ms。当前 `httpx timeout=1.5` 是分阶段超时，并非整个结束判断的 1.5 秒硬上限，这次结果再次说明总耗时可能超过 1.5 秒。

## 400 ms 断句对照

只测识别阶段，未生成回复，每个请求单独指定 `end_silence_ms=400`。

| 轮次 | 说完 → ASR final | 最终识别 |
|---|---:|---|
| 1 | 487 ms | 介绍一下绿色江河。 |
| 2 | 377 ms | 介绍一下绿色江河。 |
| 3 | 450 ms | 介绍一下绿色江河。 |

中位数 450 ms，比 800 ms 配置的 800 ms 少约 350 ms。这里只验证了一个短句；更短断句在真人停顿、长句中是否提前截断，需要另测。尚未测 400 ms 配置下的完整首音频延迟。

## 资源采样与改进方向

主测试期间取了连续 45 秒资源样本（每 5 秒一次）：整机 CPU 区间利用率中位数约 5.75%，范围 3.39%—7.69%；可用内存约 9.02—9.03 GiB。embedding 进程 RSS 约 2.17 GiB，Web 进程约 346 MiB。采样粒度不能排除短时尖峰，但未见持续 CPU 或内存压力。

1. 最直接可量化的方向是缩短断句等待；本次 400 ms 对照在识别阶段节省约 0.35 秒，应用前应以真人停顿样本确认。
2. Qwen 结束判断位于回复前的串行路径，正常问题增加约 0.74—1.21 秒；可考虑增加真正的总耗时预算，或让判断与检索并行，并保持用户指定的 Qwen 语义判断。
3. 首音频还受云端回复速度影响：本次 meta 到首音频约 0.96—1.43 秒。需要用更多时间段和真实问题测波动；小样本不报告 P95/P99。
4. 目前检索预取有效，优先保留。扩大知识库后再重测检索，不能据当前 3 个向量块推断大库表现。

浏览器 PCM 播放器会设置至少约 30 ms 的调度提前量，另有浏览器、系统和音频设备缓冲。以上首 PCM 到达时间不能直接当作扬声器实际出声时间；唤醒、实体麦克风、ROS 音频节点及表情绘制帧延迟也未纳入本次基准。
